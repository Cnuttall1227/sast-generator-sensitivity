# Generator Sensitivity in Python SAST Benchmarking

# What this is
Free static application security testing (SAST) tools are widely used to find security vulnerabilities in Python code. Recent work has measured how well they actually perform, and the answer is: not very. Liu et al. (ICSE '26) found that no single tool detected more than 40% of vulnerabilities in real-world Python code, and that aggregating all eight tools they evaluated still reached only 66.7%.

Their evaluation used two benchmarks. The real-world benchmark comprises 108 manually verified CVEs. The synthetic benchmark comprises 240 programs — 120 vulnerable and 120 patched counterparts which was all generated by a single model, DeepSeek-V3, from a single prompt.

This raises a question the original study does not address: are the reported tool scores a property of the tools, or partly a property of the model that wrote the test code? Different models have different coding habits. A pattern-matching analyzer only fires on patterns its rules cover, so a shift in generation style could move a tool's measured score without the tool changing at all.

This project regenerates the synthetic code benchmarks using additional language models, holding everything else constant, and tests whether the published tool rankings hold. 

# Research Questions
RQ1: Do the precision, recall and F1 scores reported for free Python SAST tools replicate when the synthetic benchmark is regenerated by a different model using the same prompt?
RQ2: Does per-CWE coverage shift across generators, and if so, which tools and weakness classes are most affected?
RQ3: Does the complementarity of tools hold across all generators

# Method
Score, scoring, and corpus are inherited from Liu et al. so that results are directly comparable to the published figures.

- **Weakness classes (6, from the 2024 CWE Top 25):** CWE-77 command injection, CWE-502 unsafe deserialization, CWE-94 code injection, CWE-79 cross-site scripting, CWE-22 path traversal, CWE-89 SQL injection
- **Scoring rule:** method-level. An alert matching the ground-truth type and location in the vulnerable version is a true positive; any report on the patched version is a false positive; silence on the vulnerable version is a false negative
-  **Tools:** free and no cost only, at default configuration, versions pinned
-  **Generation protocol:** One prompt set issued verbatim across models, temperature fixed, one generation per prompt per model, model versions, and dates logged, refusals recorded rather than re-prompted (following Tony et al., TOSEM 2025)

### Tools evaluated

| Tool | Version | Detection technique (Liu et al. Table 1) |
|---|---|---|
| Bandit | 1.8.0 | pattern matching + heuristic |
| Bearer | 1.49.0 | pattern matching + heuristic |
| CodeQL | 2.20.0 | taint analysis |
| DevSkim | 1.0.59 | pattern matching |
| Dlint | 0.16.0 | pattern matching |
| Semgrep | 1.101.0 | pattern matching |

Pysa and Snyk, the other two tools in the upstream study, are excluded. Reasons and
supporting citations are in `patches/versions.md`.

## Reproducing

**1. Clone the upstream benchmark.**

```bash
git clone https://github.com/Victor725/PySASTBench.git
```

The real-world dataset, which this study does not use, is distributed separately at
<https://zenodo.org/records/17936545>.

**2. Apply the patches.** Copy each file from `patches/` to its upstream path. The
mapping is listed at the end of `patches/versions.md`. The DevSkim image also needs
the CLI 1.0.59 Linux release extracted into its build context; see
`patches/versions.md`.

**3. Build the tool images.** Docker is required. Images build per tool from
`SASTTools/<Tool>/Dockerfile`. On Apple Silicon, containers run under
`--platform linux/amd64`.

**4. Scan and score.** Each arm has its own script pair, and the pair, the corpus
and the results directory must match:

| Arm | Scripts | Corpus | Results |
|---|---|---|---|
| DeepSeek-V3 | `evaluate_baseline.py` / `parse_baseline.py` | upstream `SyntheticDataset/` | upstream `Synthetic_experiment/` |
| GPT-Sol 6.1 | `evaluate_gpt.py` / `parse_gpt.py` | `corpus/GPT-Sol-6-1/` | `results/gpt-sol-6-1/` |
| Claude Opus 5.5 | `evaluate_claude.py` / `parse_claude.py` | `corpus/Claude-Opus-5-5/` | `results/claude-opus-5-5/` |

Paths are set at the top of each script as `Synthetic_dataset_path` and
`Experiment_Root`; `parse_*.py` additionally sets `Ori_Ground_Truth_path` and
`GroundTruthPath`. Adjust them to your own checkout before running.

```bash
cd PySASTBench/scripts/evaluate/Synthetic
python evaluate_claude.py <Tool>          # scan
python parse_claude.py   <Tool> evaluate  # score
```

`<Tool>` is one of `Bandit`, `Bearer`, `Codeql`, `DevSkim`, `Dlint`, `Semgrep`.
